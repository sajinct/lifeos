# LifeOS architecture and milestones

## Delivery boundary

Phase 1 provides a deployable Angular shell, real Supabase authentication, profile editing, workspace creation and switching, access control, private Storage, and a dashboard. All fifteen original ERP module areas now have working features. The remaining roadmap deepens those modules and adds broader imports and smart features; unimplemented features have no empty routes.

## Conventions

Angular 22 standalone components, strict TypeScript, signal state, lazy routes, reactive forms and Tailwind. Components render state and delegate mutations to typed repositories. No application API server. Browser configuration contains only the Supabase URL and publishable key. Hash routing supports GitHub Pages. The PWA caches build assets only; no API responses or user uploads.

## Ownership and schema

Every domain record has a UUID, workspace_id, owner_id, visibility, timestamps and foreign keys. Visibility defaults to private. A private record is readable/editable by its owner, provided that user remains a workspace member; a shared record is readable by members and editable by its owner or workspace owner. Viewers cannot create or edit. The workspace owner alone manages membership through an authorization-checking RPC. Direct ownership, workspace and role mutations are disallowed by column grants and RLS. Profiles and preferences are personal. Member identity is available through memberships; other users' profiles remain private.

Projects connect tasks, events, notes and transactions through composite foreign keys including workspace_id. A database trigger additionally verifies that a creator can access linked projects. Finance uses NUMERIC(14,2); account transfers use a single authorized PostgreSQL RPC and deterministic row locking. Account balances derive from immutable ledger entries, never client-side running totals.

Foundation: profiles, workspaces, workspace_members, categories, tags, entity_tags, attachments, reminders, notifications, activity_logs, app_settings. Working slice: projects, tasks, calendar_events, notes, goals, accounts, transactions. Additional domains will get normalized schemas with their own reviewed migrations at implementation time.

Finance planning adds private budgets, bills and recurring_transactions. Budgets match category, calendar month and account currency against the complete visible expense ledger. Bill posting locks the bill, inserts one linked expense and stores its transaction ID in the same transaction. Recurrence posting locks each schedule and uniquely identifies occurrences by schedule/date. Dates are calculated from the original anchor so January 31 returns to March 31 after February. Only the record owner with write access may post or pause; service-only automatic dispatch also checks the owner's current membership. Browser clients cannot change payment state, occurrence counters or posting dates. Plans default to manual posting, with explicit opt-in automatic hourly dispatch through Supabase Cron.

## Shared UI

The private file library reserves attachment metadata before uploading immutable bytes to Storage. Completion checks actual object size/type and promotes the reservation through an owner-authorized RPC. A new version links to its predecessor and archives it only after successful upload. Archives preserve bytes and can be restored; only unfinished/cancelled uploads can be cleaned up. Receipts may link to an immutable ledger entry owned by the uploader in the same workspace. Downloads use the authenticated Storage API, rechecking current membership rather than exposing a reusable signed/public URL. Responses bypass the browser HTTP cache. Downloaded bytes and temporary download URLs stay out of shared record signals, exports and PWA caches; file selections are transient form state. Demo blobs are memory-only and cleared with the session.

Responsive navigation, icons, toast feedback, accessible quick-add dialog, command/search dialog, theme switch, offline status, validation states and reusable record views. Dashboard widgets can be hidden in Settings. Demo records are synthetic and live only in memory; real records are never written to browser application caches.

## Deployment and operations

GitHub Pages is the requested production host. Sites hosting is not used. CI checks formatting, lint, unit tests and Supabase database tests before deploying an artifact. Local Supabase runs the same migrations and tests as production. Cloud resources and GitHub repository provisioning require the user's account configuration. PostgreSQL backups and private Storage object backups are separate, independently restorable operations.

22. Credit-card billing adds owner-private credit_cards, card_statements and card_payments with membership RLS, SELECT-only browser grants and authorized RPC writes. Card creation atomically creates an owned account with negative opening debt. Account/currency bindings stay fixed. Card and statement saves use stable request IDs and revision checks. A bank-confirmed full statement snapshot never posts expenses; only one statement is open per card and newer cycles supersede prior snapshots. Current remaining/minimum amounts subtract all nonvoid card payments dated after closing, including payments recorded against prior statements. Historical snapshots retain their own payment attribution. Card payments atomically create two immutable transfer legs and metadata, enforce owner/currency, latest-statement/date/precision limits, and cap payment at both current statement remaining and recorded ledger debt. Account row locks serialize balance checks with ledger inserts. Generic transfers involving cards direct callers to allocation-aware payments. Voids keep the original transfer and create one reversal pair; newer statements must be cancelled before correcting older payments. Cancelling a current statement with no active payments restores its predecessor. Archiving requires cleared ledger/current statement; archived card ledger postings are rejected and recurring posting is skipped until restoration. Billing reminders require both card opt-in and global Bill reminders, use existing lead days/hour/time zone, and clear on full payment, reschedule, rollover, archive or opt-out. Records page links, exact reminder routing, global card search, full 500-row pagination, session guards, memory-only demo caches, CSV and workspace JSON exports complete the feature. Billing days suggest month-end-clamped dates only; no interest calculation, bank import, automatic statement generation, payment execution or card-to-card transfer support.

23. Wealth & investments adds investment_holdings, investment_entries, wealth_exclusions, wealth_asset_values and wealth_snapshots. All five tables have private owner-plus-membership RLS, SELECT-only browser grants and authorized RPC writes. Initial holding cost/value/date/currency are immutable and do not post cash. Chronological append-only entries increase both value and basis for contributions, reduce value by withdrawal proceeds and basis by user-entered removed cost, or replace total market value for valuations. Parent locks, expected revisions, sequence numbers and stable request IDs protect state/replay. Cash-funded entries validate an owned same-currency non-card account and record one transfer leg; the other side is the holding's value, so cash movements do not become new expenses/income. Zero-proceeds loss disposals can remove cost basis without a bank entry. Undo operates only on the newest active entry, restores its before-state, retains history and posts an immutable reversal for tracked cash. Archives require zero value and zero basis. Realized gain is proceeds minus removed basis; unrealized gain is current value minus remaining basis, without tax-lot or return-rate calculations. Net worth uses owned accounts through profile-local today, current holding values, active assets at matching-currency manual values (purchase cost fallback), and remaining lent/borrowed principal. Signed negative accounts include card debt exactly once; statement totals and future loan interest are excluded. Explicit per-source exclusion records resolve representations duplicated across modules without mutating source data. Snapshots derive all currency totals in one server query and preserve capture-time totals independently of later edits; they never accept client-supplied totals. Client summaries use the same formula with safe integer cents, full pagination, session guards, memory-only demo caches, current/entry/snapshot CSV exports and workspace JSON. Valuations are manual, wealth scope is the current workspace, no currencies are combined, and no market-price service, exchange rates, tax advice or broker execution is introduced.

## Finance CSV imports

Finance’s **Import transactions CSV** opens `/finance/import`. Each file targets one caller-owned account in the current workspace. UTF-8 CSV parsing handles a BOM, reordered headers, quoted commas, escaped quotes and multiline fields; malformed quoting, unexpected/missing/duplicate columns, files above 1 MiB and more than 500 rows are rejected. Preview validates ISO dates from 1900 through profile-local today, positive unrounded two-decimal amounts below one trillion, exact account currency, income/expense kinds and bounded titles/categories/references. Invalid and duplicate rows cannot be selected. Files remain in the browser; only selected structured rows are submitted.

`finance_import_batches` has owner/membership RLS and SELECT-only browser access. `import_finance_csv` verifies current write membership and account ownership, rejects archived cards, independently validates the payload and inserts the whole batch in one database transaction. It locks the stable batch ID and then the account, serializing overlapping imports with other ledger inserts. Retrying the same ID/payload returns the original result; changed account/workspace/owner/payload is rejected. An invalid later row rolls back all previous rows and batch metadata. A failed refresh preserves the prepared request for retry. Workspace/session changes discard previews and ignore late results.

Imported transactions retain optional `import_batch_id` and `import_reference` metadata. References are unique per owner/workspace/account. Reusing a saved reference with different transaction contents rejects the entire batch. Exact date/title/kind/amount/category matches are conservatively skipped, including existing manual entries and duplicates within or across files. Currency follows the immutable account. There is no duplicate override; genuinely identical purchases can be entered individually in Finance. A reference on a skipped manual match is not attached retroactively. Imports do not change account opening balances or generate transfers, loan allocations, card payments or investment entries. They do not execute payments. Demo uses memory-only batches and mirrors all-or-nothing/retry behavior. Broader JSON imports and automatic bank connections remain pending.

## Finance JSON imports

Finance JSON imports are an additive subset of LifeOS workspace exports, with 1–50 source accounts, at most 500 transaction rows and a 5 MiB UTF-8 file limit. The browser reads `accounts` and `transactions`, identifies exported cards from `creditCards`, and lists populated sections it leaves out. Only ordinary unlinked income/expense rows are supported. Transfers and rows linked to projects, loans, subscriptions, bills or recurring schedules remain excluded. This is not a complete workspace/database restore; omitted movements can change reconstructed balances. Source owner/workspace IDs, record IDs, timestamps, sharing and unsupported foreign keys never become permissions or destination identifiers.

The user maps each source account to an owned same-currency account or explicitly chooses creation. Existing names/opening balances are never updated. Creation applies the validated exported opening balance, including negative cash balances. Exported cards require an existing active owned credit-card destination; card metadata/statements/payments are not restored here. Saved mappings are immutable. Raw source names/balances in later exports do not overwrite destination metadata. Preview supports row selection, flags invalid and unmapped records, and conservatively skips identical ledger entries or references. Identical-looking legitimate purchases remain separately enterable in Finance.

`finance_json_batches` and `finance_json_links` have owner/membership RLS and SELECT-only browser grants. The JSON RPC serializes source-binding creation per caller/workspace and locks existing account destinations in UUID order. All account creation, nested validated CSV postings and source links run in the same database transaction. Failures roll back the entire batch, including new accounts and the nested import audit rows. The stable batch ID/payload returns its original result on replay; changed identities, account bindings or payloads are rejected. Transaction source IDs retain canonical contents and a destination-ledger link; altered contents are rejected. Source IDs can be portable strings up to 200 characters and confer no authority. Linked existing manual duplicates remain immutable. The frontend pages source links in stable 500-row chunks and guards preview/file/save callbacks against workspace/session changes. Demo uses only memory and mirrors atomicity and source binding rules across workspace switches. PWA caches contain no imported real data.

## Tasks and Notes JSON imports

The `imports/tasks-notes` route accepts LifeOS exports with `tasks` and/or `notes` arrays: 1–500 combined records, up to 50 referenced source projects and 5 MiB of UTF-8 JSON. Tasks retain title, status, priority and nullable due date. Notes retain title and literal body text, including whitespace, with a 100,000-character body limit. Dates may be planned in the future but must be real ISO dates in 1900–2100. Source IDs are unique per record kind, 1–200 characters. Missing/duplicate identities reject the file; invalid content rows are reviewable and cannot be selected.

Project metadata is used only to label links. Original accessible IDs or a unique exact project title may be suggested; otherwise the user must map to an accessible destination project or explicitly unlink. Private projects owned by another member and cross-workspace destinations are rejected. Shared readable projects may be linked without granting project members access to imported private children. Saved mappings are fixed per caller/workspace/source project. The prepared payload contains only selected records and the project mappings those records require.

`record_json_batches` and `record_json_links` have owner/membership RLS and SELECT-only browser access. The import RPC checks current write membership, strict payload columns/types, title/body/date constraints and current project readability. A stable request ID protects retries, and the existing workspace task lock serializes imports with task structure edits. Project rows are locked in UUID order. Source IDs never become destination IDs or authorization fields: imported task/note UUIDs are generated by the server, ownership comes from `auth.uid()`, and visibility is always private. Imported tasks have default revision 1 with no assignee, list, recurrence or occurrence index. Task warning rows and omitted-section summaries explain structural features that are not restored. No sharing, assignments, reminders, time records, attachments, tags, lists or checklists are restored by this import.

Each batch atomically creates private task/note rows and immutable source links. Invalid later rows roll back everything. Exact private duplicates are skipped; shared records and another member’s records are never reused as private duplicate destinations. Changed source IDs or existing private record identities are conflicts. Reuploading unchanged source data preserves subsequent destination edits and deletions, with nullable destination foreign keys retaining source identity after normal deletion. Private batch/source audit metadata retains the original imported content for retry/conflict detection; deleting a note from the Notes view does not purge that import metadata. There is no import undo or destructive overwrite mode. Real imported data never enters PWA caches, and previews/file reads/reloads are guarded against session/workspace changes. Demo metadata remains in memory and follows workspace isolation. Notes now use stable complete pagination before newest-first display, so older records participate in previews, exports and duplicate checks; Calendar now also uses stable full pagination, as described below.

## Opt-in email delivery

Account-level `email_preferences` defaults all channels off, with independent reminder, daily, weekly and financial opt-ins. Revision-checked saves derive the owner from Auth, validate IANA zones, retain activation timestamps and never backfill pre-opt-in notices. New opt-ins require a verified Auth email and configured server sender; opt-outs remain possible during provider outages. Each workspace produces its own email with only that recipient's own records. Membership removal revokes history and stops queued mail. Supported reminder kinds are tasks, bills, credit-card statements, subscriptions/trials and document expiry. Health, medication and other personal reminder kinds remain in-app. Read/dismissed/stale/completed sources cancel pending emails, and snoozes defer claims.

The service-only queue calls the existing reminder dispatcher and enqueues at most 500 new reminder occurrences and 500 eligible preference/workspace pairs per run. Already queued periods are excluded before these bounds, avoiding starvation. Daily/weekly planning includes up to 20 owned open tasks and 20 owned events; the daily window is today and weekly window is the next seven calendar days, including overdue/undated tasks. Financial summaries cover the prior seven completed days or previous calendar month, sum owned income/expenses by account currency and exclude transfers. The scheduler follows explicit local hour, weekly day and timezone; monthly delivery is on the first day. There is no historic summary backfill.

At first claim, plain-text sender/recipient/subject/body are frozen and every retry uses the same Resend idempotency key. Email changes invalidate frozen recipients. Retries stop after five attempts or 22 hours from first attempt, inside Resend's 24-hour idempotency retention; uncertain deliveries are not automatically resent later. Provider acceptance is distinct from inbox delivery, and bounce/delivery webhooks are not implemented.

The `email-dispatch` Edge Function independently verifies a private 256-bit scheduler header before touching any data. It uses built-in server credentials, never frontend keys for privileged RPCs, and processes at most ten claims within a bounded run. API errors are stored as safe codes without response bodies or private content in logs/results. Provider credentials are Edge secrets. The scheduler key is installed in Edge secrets and Supabase Vault, and Cron invokes the function through pg_net every five minutes. Anonymous/user JWT requests are rejected by the function even though gateway JWT verification is inapplicable to this custom scheduler header. The setup probe checks server configuration without queueing or sending mail. Demo settings remain memory-only and send nothing.

### Education and school fees
