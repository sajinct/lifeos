# Setup, deployment, and recovery

## Task assignments and personal time

Open a shared task's **Details** and use **Assigned member**. Only its creator or workspace owner can set/clear assignment. Options are current workspace members identified by display name (or a short member ID when unnamed) and role. The directory reveals no emails or private profile settings. **Assigned to me** filters tasks. Assignment labels responsibility; it does not give task access or status/checklist edit rights. All members may already read shared tasks; only the creator and workspace owner may edit those tasks. Members with write access can log their own time against readable tasks. Viewers remain read-only. Private tasks cannot be assigned, making a task private clears assignment, and removing a member clears their assignment. Household labels are separate from these authenticated workspace members.

**Your time & productivity** on Tasks/Inbox holds a task selector, work date, whole minutes (1–1440), notes and **Record manual time** / **Start timer**. Date/minutes apply to manual entries; the timer starts at the current server time. It continues across navigation/reload, with one running timer per user/workspace. **Stop timer** saves once; repeated starts/stops cannot duplicate records. Elapsed time caps at 24 hours and longer work needs separate sessions. Timer work date is the profile's local date at start; overnight sessions are not split across days. Multiple workspace timers are independent. Timers do not automatically finish tasks or post financial entries.

All time records are private to the logger plus current workspace membership, even for shared tasks; workspace owners cannot see other members' logs. **Edit** changes recorded manual duration/date/notes with revision checks and keeps its original task/project names. **Discard** retains a reversible history row excluded from totals; **Show discarded entries** exposes **Restore**. Discarding a running timer stops it and permits later restore as a completed session. Demoted viewers/removed members cannot modify logs or stop timers until workspace write membership is restored. New timers in other workspaces remain independent.

Date filters and **Summarize by Task/Project** report completed, recorded sessions only. Snapshots retain names known when logged, even if a task is renamed, deleted or becomes inaccessible; they do not restore task access. A deleted task leaves a detached but editable personal manual log. CSV follows date/discard filters, excludes running sessions and neutralizes spreadsheet formulas. Workspace JSON includes every visible time record via full pagination; no time data goes into static PWA caches. Apply `202610120012_task_assignments_time.sql` before deployment and run `scripts/task-work-cloud-smoke.sql` for rolled-back live privacy/retry checks.

## Task lists, subtasks and recurring tasks

Open **Tasks** or **Inbox**. Add a private task list, then open a task's **Details** to assign it to a list. Lists support rename/archive/restore. Archived lists retain their tasks and can still be filtered/exported, but cannot receive new assignments. Remove a task from an archived list by choosing Unlisted or an active list. One-off quick capture and Kanban remain available.

Add, edit, check/undo or remove checklist steps (maximum 100 per task). Checklists inherit the parent task's visibility and creator/workspace-owner editing roles. Other editors/viewers may read shared checklists; private checklists stay private even from workspace owners. Checklist completion is independent of parent status. Reopen a completed parent before editing its steps.

For a private, pending task you own with a due date between 1900 and 2100, choose daily/weekly/monthly/yearly under **Repeat task**, then **Save organization**. This fixes the frequency and original date anchor. Completion atomically creates one next dated task and copies every checklist step as unchecked. Jan 31 monthly repeats become Feb 28 then Mar 31; Feb 29 annual repeats clamp to Feb 28 in non-leap years. A late completion creates the next scheduled occurrence, even if that date is already overdue; it does not flood the inbox with every missed date. Existing successor tasks survive reopening, so retrying or completing again cannot generate duplicates. Parent completion does not require all steps checked.

**Pause repeat** prevents new generation and keeps existing tasks. **Resume repeat** generates one missing successor if the latest occurrence was completed while paused. Existing tasks can be moved between active private lists; their title/priority/project/list/checklist are copied from the completed occurrence. Recurring due dates/sharing remain fixed. To change a repeat's anchor/frequency, pause it and create a separate task. Repeats automatically stop when the next date would exceed 2100. Successors drop a project link if it has become inaccessible. No task scheduler, email, time tracking or account-based assignments are introduced here.

**Export tasks CSV** follows the search/status/list/current-source filters, includes steps and repeat metadata, and neutralizes spreadsheet formulas. Settings workspace JSON includes all visible tasks, lists, series and checklist records with complete pagination. Apply `202610120011_task_productivity.sql` before deploying this frontend. Run `scripts/task-cloud-smoke.sql` for rolled-back synthetic verification.

## Goals, habits and routines

Open **Goals & habits**. Goals support long-term, monthly and annual periods, numeric target/current/unit, optional notes and a target date (required for monthly/annual). A period labels the target; progress is never automatically reset. New goal forms are private. Existing shared goals retain sharing and the established creator/workspace-owner editing permissions. Archive/restore retains progress and milestones and removes archived goals from the overview.

Milestones are private to the goal creator even under a shared goal. Completing/reopening records/clears the creator's local completion date; it never changes goal progress. Editing or completing milestones requires an active owned goal and write membership. Archives freeze the checklist until restoration. Goal, habit and milestone saves use request UUIDs/revisions; stale screens should refresh before retrying.

Habits have a title, routine label (Morning, Evening, etc.), notes, start date and selected ISO weekdays. Blank routine names appear as Ungrouped. Start must be today or earlier; schedule/start are fixed after creation so later edits cannot rewrite history. Create a separate habit to change its schedule. Habit metadata, lifecycle periods and check-ins are private, even in shared workspaces. Pause/resume/archive changes apply from the profile's current local date. Multiple status changes on the same day retain the final state for that day, while check-in history stays saved. Pausing/archiving removes today's scheduled requirement; resuming may make today scheduled again. Archived habits cannot be checked in until restored. Paused habits permit correcting earlier active dates, but not paused dates.

Check-in date permits today and the previous 365 days, starting no earlier than the habit's start. Future, unscheduled and inactive dates are rejected. Complete/undo has one row per habit/date; retries are idempotent, and stale actions cannot undo a newer change. Current streak counts consecutive completed scheduled days, skips weekends/non-selected and paused dates, and gives an unfinished today until the day ends. Best streak covers the last 90 calendar days. Consistency is completed/required scheduled days in the last 30 calendar days, including today. Statistics follow historical lifecycle periods, and the displayed aggregate excludes currently archived habits. No habit email or scheduled reminder is added in this milestone.

Goal and habit CSV follows current filters/selection; **Export check-ins** includes all saved true/false check-ins for visible habits. Text prefixes are neutralized for spreadsheets. Workspace JSON includes all goals, milestones, habits, periods and check-ins, with full pagination and session guards. Apply `202610120010_goals_habits.sql` before deploying; `scripts/habit-cloud-smoke.sql` verifies synthetic, fully rolled-back owner isolation, retries, progress/milestone independence, check-in revisions and pause history.

## Career and professional records

Employment, applications and certifications are private to their creator, even in shared workspaces. Use Career to record employment dates and skills, application stages and dates, and certificate issue/expiry dates. Dates support 1900–2100; employment and application/issue dates must be today or earlier in the profile time zone. Interviews use day reminders; store exact appointment times in Calendar.

Link up to 50 own ready/archived files in the current workspace. Links retain the exact selected version. A renewed CV or certificate must be selected explicitly. Storage access remains private, and no bytes are cached offline.

Enable Career reminders in Settings. Follow-ups and interviews have a shared lead time; certification expiry has a separate one. Defaults are disabled. Accepted, rejected, withdrawn and archived applications stop notices. Follow-up done and Interview done clear the respective date with revision protection. Archive keeps all details and links. Restore as applied explicitly reopens an archived application; adjust its dates/status as needed. Archived certifications stop expiry alerts. Reusing an already delivered source/date/phase does not issue that notice again.

Application changes do not send messages, create employment or post Finance entries. CSV follows the visible section/search/status filter (or selected reminder record), escapes spreadsheet formulas and includes document names/IDs. Workspace JSON contains all accessible career records and links through full pagination. File bytes require the existing separate Storage backup. Live verification is in scripts/career-cloud-smoke.sql and rolls back synthetic identities/records.

## Assets & maintenance

Open **Assets & maintenance** to add an appliance, electronic device, vehicle or other possession. Store name/category, make/model, serial or registration number, location, optional purchase date/price/currency, warranty end and notes. Purchase must be today or earlier; warranty must follow purchase when known. Prices use non-negative amounts with at most two decimal places, below one trillion. The register is private to its owner, even in family workspaces; workspace owners cannot read another member's assets. Viewers can read their previously owned records but cannot write. Removed members lose access.

Link up to 50 of your completed **Documents & receipts** in the same workspace, including archived versions. The selector pages all eligible metadata; no file bytes are fetched. Opening a link fetches the exact owned file when outside the generic library window and opens its correct receipt/document library. File versions, archives, ownership, authenticated downloads and Storage permissions are unchanged by linking. Upload new files from the file library. Asset links stay with the selected version until you edit them; archiving/replacing a document does not automatically reassign them.

Choose **Maintenance & history → Add maintenance plan** for a one-time, monthly or yearly service. **Record service** stores the actual performed date, optional cost and notes, and advances the due occurrence once. Service history is immutable: check details before saving. It preserves scheduled/performed dates, service title and cost/currency snapshots. Reference costs do not create Finance expenses or change balances; capture an expense separately only if needed. Repeating dates retain their original anchor (January 31 → February 28 → March 31). Early completion advances from the scheduled date, and overdue occurrences advance one at a time. Editing next date/frequency resets the anchor/counter while preserving history; already completed scheduled dates cannot be reused. A future cursor that collides with old history is rejected, with an instruction to edit the schedule. One-time completion closes the plan; add a new plan for a later one-time service. Pause/resume preserves due dates. Schedule dates are supported from 1900 through 2100; completion rejects advancement beyond that range.

**Mark sold**, **Retire**, and **Archive** preserve documents, plans and history and stop all asset reminders. **Restore to active** re-enables active schedules, whose dates may already be overdue; paused/completed plans stay in their prior state. Metadata can be edited only on active assets. Integer revisions reject stale edits/completion, stable creation/service IDs make retries safe, and no direct browser writes are granted to asset tables or logs.

Enable **Asset warranties and maintenance** in **Settings → Reminders**. Warranty and service lead times are independently configurable from 0–90 days; the existing personal hour/time zone and five-minute in-app dispatcher apply. Expired warranties and overdue services have separate notices. Completion, pause, retirement and date edits clear stale alerts. Restoring/resuming the same source/date/phase does not resend a notice already delivered/dismissed. Reminders open the exact asset and, for services, identify the specific plan. Older settings RPCs preserve asset preferences. Email delivery is not part of this milestone.

**Export assets CSV** follows register search/status/category filters. **Export maintenance CSV** includes the selected asset's schedules and history. Workspace JSON includes every visible asset, document relationship, schedule and service record. Full pagination prevents silent truncation, exports stop on loading errors, and text uses spreadsheet formula-prefix escaping. Demo data stays in memory and PWA caching includes static assets only. Apply migration `202610120008_assets.sql`, then run `supabase db query --linked --file scripts/asset-cloud-smoke.sql` for a rolled-back live check of privacy, atomic file links, replay/revision safety, anchored dates, Finance isolation and reminder cleanup. The check creates no Storage bytes, email or credentials.

## Family & household

Open **Family & household** and choose **Members & birthdays**, **Responsibilities**, or **Important dates**. Household members are name/relationship records, not login identities: adding or assigning one does not invite them, alter access, send messages, or synchronize Contacts. Birthdays store month/day only. Date-only displays preserve the calendar date across browser time zones. Yearly dates and birthdays retain their original month/day, observe February 29 on February 28 in other years, and roll forward after the occurrence day. One-time responsibilities and dates remain overdue until completed/archived or edited.

Every record starts **Private — only me**. **Shared — entire workspace** exposes all record fields (including notes) to current and future workspace members. Use a dedicated Family workspace and manage authenticated members in Settings. A record creator with write access can edit it and change sharing; the workspace owner can edit shared content but cannot change another creator's sharing. Other editors and viewers can read shared content; viewers cannot create or edit. Workspace owners cannot read member-private records. Removing membership revokes access. Responsibilities are assigned to household record labels, not account identities or extra permission grants.

Shared responsibilities/dates may link only to shared household members. A member cannot become private while any shared entry (including an archive) retains its link: unlink those entries or have their creators make them private first. Archiving a member stops birthday alerts and blocks new assignments, while existing linked entries remain intact. Responsibilities support **Mark complete**, **Reopen**, and archive/restore; important dates support archive/restore. Restoring an archived completed responsibility reopens it. Integer revisions prevent stale edits/completion and stable creation IDs make retries safe. Browser table writes are denied; authorized RPCs serialize relationship and sharing edits atomically.

Enable **Family birthdays, responsibilities and dates** in **Settings → Reminders**, choose 0–90 lead days, and save. The existing five-minute dispatcher uses personal delivery hour/time zone and sends private in-app alerts to the record creator only, including when a source is shared. Household labels and workspace readers do not receive another creator's notifications. Completion/archive and date changes clear stale notices; annual rollover clears the prior year. Reopening/restoring the same source/date/phase does not re-send an already delivered/dismissed notice. Older reminder-settings RPCs preserve family preferences. Notifications link to the exact household record.

**Export household CSV** respects the selected section, search, status and visibility filters. Workspace JSON includes all visible household records. Full pagination prevents silent export truncation; exports are disabled while loading or on errors. No personal data is cached by the PWA, and demo edits are memory-only. Apply migration `202610120007_household.sql`, then run `supabase db query --linked --file scripts/household-cloud-smoke.sql` to check sharing, atomic links, retry/revision safety, completion, annual delivery and viewer/removed-member isolation inside a fully rolled-back synthetic transaction.

## Local development

Run `npm ci`, then `npm start`. Open http://127.0.0.1:4200 and choose **Explore a demo workspace**. Demo data is synthetic and held in memory. Reloading or signing out clears it. Only the theme preference and Supabase's own auth session persist in browser storage.

## Connect Supabase

1. Create a Supabase project, then install the official Supabase CLI.
2. Use `supabase login`, `supabase link --project-ref YOUR_PROJECT_REF`, and `supabase db push` from this directory. Review the migration before applying it to an existing project.
3. Set public build variables. PowerShell:

```powershell
$env:SUPABASE_URL = 'https://YOUR_PROJECT.supabase.co'
$env:SUPABASE_PUBLISHABLE_KEY = 'sb_publishable_YOUR_PUBLIC_KEY'
npm start
```

`.env.example` describes variables; it is not automatically loaded. Only a publishable key or legacy anon JWT is permitted by the build script. A secret or service-role key is rejected. Frontend build variables are visible in public assets, even when sourced from GitHub Secrets.

4. Configure Auth's Site URL and redirect allowlist for the exact development/staging/production origins and base paths, including the `?flow=recovery` reset redirect. The code exchanges a PKCE `code` in the URL before entering hash routing. Verification/reset links should be opened in the same browser that initiated them.

The scoped production configuration is tracked separately. After reviewing the diff, apply it to the intended project:

```text
npx supabase config diff --project-ref YOUR_PROJECT_REF --workdir config/production
npx supabase config push --project-ref YOUR_PROJECT_REF --workdir config/production
```

This declares the LifeOS production and local Auth redirect URLs, email signup and confirmation. Undeclared remote settings remain unchanged. Do not push the local development config as production Auth configuration. 5. Enable email confirmation, configure SMTP for production, sign up, verify your email, and sign in. A profile is created by a trigger. Create a workspace in Settings. The schema does not insert demo records into real accounts. 6. Workspace owners can add an existing account by profile UUID in Settings. This intentionally does not send email invitations or expose a searchable profile directory. Viewer access is read-only; private records are invisible to other members, including the workspace owner. Finance accounts and ledger entries remain private.

## Private files

Open **Documents & receipts** in the sidebar. Documents support PDF/JPG/PNG/TXT; receipts support PDF/JPG/PNG. Files must be non-empty and at most 10 MiB. Categories, expiry dates and optional project links organize the library. Finance rows have **Add receipt**, which opens the upload form with that ledger entry selected. Receipts may also be uploaded unlinked and linked later through **Details**. Expiry filters identify expired documents or those due within 30 days. Enable document expiry reminders in Settings; a reminder links to the document and its **New version** action for renewals.

The `personal-documents` and `financial-receipts` buckets are private. Paths are `USER_UUID/WORKSPACE_UUID/FILE_UUID.ext`. Only the uploader, while still a workspace member, can read bytes or metadata. Workspace owners do not gain access to another member's files. Viewers can read their own existing files but cannot upload or edit. Storage requires a matching owned file reservation for every upload. Upserts and object updates are disabled. Downloads use authenticated requests with browser caching disabled; there are no public file URLs or persistent signed links in the app.

**New version** uses a fresh immutable object path. Completion archives the predecessor without replacing its bytes. **Archive** hides a completed file from the current list, while **Restore** makes it visible again. The archive holds earlier versions too. There is no permanent deletion control for completed files. This preserves recovery and does not reclaim Storage space. Purging completed data requires a separately reviewed administrative retention process.

Interrupted uploads remain under **Unfinished uploads**. **Finish upload** retries metadata completion if the bytes already reached Storage. **Retry with file** reuses the reservation and requires the original filename/type/size; it does not overwrite an existing object. **Cancel unfinished** marks the reservation cancelled, removes the unfinished bytes through the Storage API, and removes metadata only after checking the object is gone. Failed cleanup stays retryable. Storage and database operations are separate services: periodically reconcile orphaned objects against attachment metadata, especially after network/process failures or concurrent uploads across browser tabs. Download failure after manual administrative object removal does not imply lost metadata; reconcile or restore from backup.

The newest 500 attachment records per workspace are loaded, including archived/unfinished versions. Workspace JSON includes their metadata, not bytes. Private file contents need separate backups. Demo uploads and versions live in memory and are cleared on reload or sign-out.

`scripts/storage-cloud-smoke.mjs` performs actual Auth/Storage integration checks using disposable confirmed identities (without sending email), synthetic files and a disposable workspace. Run only on the intended project, from a trusted server-side process with `LIFEOS_SMOKE_URL`, `LIFEOS_SMOKE_PUBLIC_KEY`, and `LIFEOS_SMOKE_SERVICE_KEY` supplied in its environment. It checks authenticated download, public/viewer denial, immutable versions, receipt links, cleanup and membership revocation, then removes its test objects and identities. Never place a server credential in public build variables, source files or logs. The connected production project passed this check. See [Supabase Storage access control](https://supabase.com/docs/guides/storage/security/access-control).

## Finance planning

Apply all migrations with `supabase db push` before deploying a frontend that loads finance planning tables. Budgets, bills and schedules are private even within shared workspaces. The latest 500 planning records are loaded per table; the expense ledger is fully paginated for budget calculations. Workspace JSON exports include loaded planning records. CSV includes the complete visible ledger. Demo planning edits are in memory, and demo recurring posting uses the explicit **Record due** button.

Bills do not affect balances until **Record paid** creates an expense. Repeating the action returns the same transaction; paid bills cannot be cancelled. Pending bills may be cancelled without creating a ledger entry. This app records payments; it does not execute bank payments.

Recurring schedules support daily, weekly, monthly and yearly income/expenses. Automatic posting is opt-in on schedule creation. **Record due** posts missed occurrences through today in the profile time zone, at most 100 per run. Monthly and yearly dates remain anchored to the original start day, clamping in short months. Pause holds the cursor; resuming catches up missed dates. Removing or downgrading the owner's membership stops posting. To change amount, account or frequency, pause the old schedule and create a new one. Avoid overlapping start dates if you do not want overlapping ledger entries.

Enable the hourly job after applying the migration:

```text
npx supabase db query --linked --file supabase/setup/recurring-cron.sql
```

The setup is repeatable for the named job. Dispatcher execution is restricted to `service_role` and database administrators; it processes at most 500 due automatic schedules per run. Monitor **Integrations → Cron → Jobs → History** in Supabase. To pause the dispatcher, toggle this job inactive. Private entries stay out of the PWA cache. See [Supabase Cron](https://supabase.com/docs/guides/cron/quickstart).

The connected production project has this hourly job enabled. Run `npx supabase db query --linked --file supabase/tests/finance-cloud-smoke.sql` to recheck live bill/recurring posting and finance isolation. It rolls back its synthetic accounts and ledger records without sending emails or touching passwords.

## Finance reports

Open **Reports & exports**. The default is the last six calendar months through today; **This month**, **Last 6 months** and **Last 12 months** reset the date filters. Custom from/to dates are inclusive and use ledger booking dates, with a maximum of 120 calendar months. The earliest and latest months can be partial. Select all currencies or one currency; no exchange-rate conversion or combined monetary total is used. Reports include only the signed-in user's records in the current workspace. Account, budget, subscription and ledger pagination avoids silently dropping older records. Loading failures disable exports and hide partial reports.

Income minus expenses is **net savings**, excluding principal and internal transfers. **Cash received/paid out/net cash flow** also includes recorded borrowed/lent principal and principal repayments from the Loans module; transfers between your accounts remain excluded. Opening balances are not cash flow for the selected dates. Monthly bars show income/expenses, with the expandable figures giving principal and net cash flow. Empty months are shown as zero, and table values remain available alongside the chart.

Category spending compares the selected period with the immediately preceding period containing the same number of days; the comparison dates are shown explicitly. Categories with no previous spending show an amount change without a percentage baseline. Budget actuals match category/month/currency/owner and selected booking dates. Their limits are the full monthly budgets, without partial-month prorating, and negative remaining amounts indicate overspending.

Recorded subscription expenses and loan interest are already included in the income/expense totals. Scheduled renewals, estimates and tracking-only repayments create no report spending. Migration `202610120005_report_attribution.sql` tags posted subscription expenses and currently linked historical expenses, preserving their original subscription label after later disconnection/reassignment/cancellation. Expenses from schedules disconnected before this migration may remain unclassified; total income/expenses still include them. Direct browser edits to ledger amounts or subscription tags are denied. Run `supabase db query --linked --file scripts/report-cloud-smoke.sql` to verify attribution preservation, unchanged ledger totals and owner/viewer isolation inside a rolled-back synthetic transaction.

**Export report CSV** contains the current date/currency-filtered summary, monthly figures, category comparisons, budget limits/actuals, subscription breakdown and matching transactions with account/source identities. It preserves cents and neutralizes spreadsheet formula prefixes. **Workspace JSON** retains the separate loaded-workspace snapshot behavior. The report does not fetch exchange rates, persist extra user data or contact a third-party analytics service.

## Loans and repayments

Open **Loans & repayments**. Enter the loan name and lender/borrower, direction, currency, principal, annual simple-interest rate (0–100%), monthly term (1–600), start and first due dates. The start must be today or earlier; the first due date must follow it. The total agreed interest is principal × annual rate × term / 1200, rounded to cents. Monthly installments round up to cents and the final installment covers the remaining total. Very small amounts require fewer installments so the final amount stays positive. Dates retain their original day, including month-end clamping. This is a fixed simple-interest contract, not bank EMI/reducing-balance amortization or compounded interest. Early repayment advances the schedule without reducing the agreed interest.

**Initial principal in Finance** defaults to **Tracking only / already recorded**. Select your own account in the same workspace/currency only if the original cash movement is missing. Borrowed principal is a transfer-in, lent principal a transfer-out; neither inflates income/expenses. Loan terms and repayment history are immutable, so verify the contract details before saving. Records and counterparty names stay private to their owner even in shared/family workspaces.

Select **View repayments** and **Record repayment**. The form suggests the next remaining installment split, but the user must enter the principal and interest actually paid according to their agreement. Partial payments retain the due date until its scheduled amount is covered. Extra payments can cover later installments; full settlement marks the loan paid and clears due reminders. Payment dates must be between the loan start and today, and each component cannot exceed its remaining balance. Choose a Finance account to record principal cash movement and interest income/expense atomically. Choose tracking only if the payment is already in Finance. LifeOS records bookkeeping; it never sends money. Successful request retries reuse the original UUID and never duplicate ledger entries. The repayment history shows its date, split, notes and linked account; the expandable schedule shows covered and remaining installments. Currencies stay separate in outstanding cards, and JSON export includes all visible loans and repayment rows.

Enable **Loan repayments** in **Settings → Reminders** with 0–90 lead days. The existing personal delivery hour/time zone, five-minute service-only dispatcher and bell actions apply. Loan reminders link to the exact loan. Due-date advancement or full settlement dismisses stale notices. Earlier reminder preference RPCs preserve loan settings. After migration `202610120004_loans.sql`, run `supabase db query --linked --file scripts/loan-cloud-smoke.sql`. It checks owner isolation, simple-interest terms, idempotent atomic posting, tracking-only mode, partial/final repayment, overpayment rejection and reminder cleanup inside a fully rolled-back synthetic transaction.

## Subscription tracking

Open **Subscriptions** in the sidebar. Add a service, its price per monthly/yearly billing period, currency, next renewal date, category and optional HTTPS provider website/notes. Select **Free trial** to track its end date and expected paid-plan price; first paid renewal must be on or after the trial end. Zero-cost plans may be tracked without an expense schedule. Records remain private to their owner, including in family/shared workspaces. Monthly and annual estimates include active plans, exclude trials/cancelled plans, and keep currencies separate; they are normalized estimates rather than recorded expenses. The complete visible subscription set is paginated for these totals.

Choose an expense-recording mode:

- **Track renewal dates only:** creates no expense entries. When due, **Mark renewed** advances one anchored billing occurrence; repeated acknowledgements of the same due date do not advance twice. Month-end dates retain their original anchor.
- **Create a recurring expense schedule:** select your own account in the subscription currency. A positive price and a first date of today/later prevent silent historical backfill. Leave automatic recording off for manual **Record due expenses**, or explicitly enable hourly expense recording in LifeOS. Recording is bookkeeping; it never charges an account or pays a provider.
- **Link an existing expense schedule:** only your monthly/yearly expense plans in the same workspace are eligible, and each may belong to one subscription. The schedule's price, currency, frequency and next date are authoritative; its automation choice stays unchanged. Existing schedules retain their original posting/backfill behavior. Replacing or disconnecting a link pauses the old schedule and preserves posted history.

Trial schedules are always paused, including when automatic recording was requested. **Start paid plan** opens an explicit edit with an active status and, for linked trials, a fresh schedule. Confirm the first paid date, account and automation choice before saving. Cancelled subscriptions can be restarted the same way, without reusing a stopped historical schedule. **Mark cancelled** should be used after cancelling with the provider; it updates LifeOS, disables the linked schedule's active/automatic flags and clears renewal/trial alerts. Posted ledger entries remain intact. Directly resuming a trial/cancelled linked schedule from Finance is rejected. Saving edits uses the last-loaded update timestamp; a concurrent change asks you to refresh rather than overwriting it.

Enable **Subscription renewals and trials** in **Settings → Reminders**, choose 0–90 lead days and save. Trial-end and paid-renewal events are distinct, so activation clears the trial reminder and can issue a separate renewal reminder. The existing five-minute service-only dispatcher, personal time zone/hour, snooze/dismiss and membership checks apply. Reminder links show the exact subscription. Provider websites are user-entered HTTPS links opened separately; LifeOS has no provider cancellation/payment integration. Use the server-side check `supabase db query --linked --file scripts/subscription-cloud-smoke.sql` after applying migration `202610120003_subscriptions.sql`; all synthetic test records and identities are rolled back without sending mail or creating credentials.

## Reminder dispatch

Open **Settings → Reminders**. Each account independently enables task, bill and document reminders across its workspaces. They default to disabled. Set lead times (tasks/bills 0–30 days; documents 0–90 days), a delivery hour (0–23), and an IANA time zone such as `Asia/Kolkata`. Saving is an owner-scoped RPC and preserves dashboard preferences. Eligible sources are the user's incomplete tasks with due dates, pending bills, and ready personal documents with expiry dates. Receipts and archived/uploading files do not generate expiry reminders.

The service-only dispatcher checks every five minutes after the configured local hour. It creates one upcoming reminder per source/date when the lead window is reached, and one overdue/expired reminder once the local date passes the due date. Enabling reminders late catches up with one current reminder rather than producing daily historical alerts. A unique source/date/phase constraint and a transaction advisory lock protect retries/concurrent runs. Existing manual reminders retain their unique `reminder_id` delivery semantics.

Notifications appear in the bell for the current workspace. **Open tasks/finance/document** shows the relevant record; **Mark as read**, **Dismiss**, and **Snooze 1 hour/1 day** operate on the original notification. The Snoozed tab shows its return time in the browser's local time zone. Snoozed notices return unread when their timestamp is reached. The app refreshes notices on bell opening and every minute while visible; delivery and display may therefore take several minutes. The newest 100 non-dismissed notices are loaded per workspace. Dismissal persists and does not recreate the same occurrence. Completed tasks, paid/cancelled bills, archived documents, and changed due dates clear stale notifications; disabling a reminder type also clears existing notifications of that type. Restoring a source with the same due date does not recreate a dismissed occurrence. A new due date or renewed document version is a new occurrence.

Reminder titles and actions stay private to the source owner, including for shared source records. Current workspace membership is checked for reads, actions and dispatch; removal revokes access immediately. Email is a separate future milestone; SMTP configuration alone does not enable reminder emails.

Migration `202610120002_automated_reminders.sql` installs/updates the named `lifeos-reminders` cron job when `pg_cron` is present. It is active on the production project. For a new project, enable the `pg_cron` extension in Supabase and schedule:

```sql
select cron.schedule('lifeos-reminders', '*/5 * * * *',
  'select public.deliver_due_reminders();');
```

Verify activation/execution with `select jobname,schedule,active from cron.job where jobname='lifeos-reminders';` and the corresponding `cron.job_run_details` history. Run the server-side smoke check with `supabase db query --linked --file scripts/reminder-cloud-smoke.sql`. It tests real scheduler grants, retry protection, snooze, task/bill lifecycle and viewer isolation using synthetic identities inside a rolled-back transaction; no email or credential is created. Reminder dispatch is separate from recurring finance. Future email delivery should use an authenticated server-side outbox with retries and provider idempotency keys. Secrets belong in Supabase server-side configuration.

## Project planning

Open **Projects**, create a private/shared project with status, deadline and notes, then choose **Open project**. Milestones follow the project's visibility and edit roles. Each has a title, optional deadline/notes, independent completion date and reversible archive. Completing milestones does not complete linked tasks or change project status. Reopen a completed project before editing its milestones. A shared project cannot become private while shared tasks, events or notes link to it. Existing creator/workspace-owner edit rules apply; being assigned a task does not grant project edit access.

**Your budget & expenses** is personal even under a shared project. Add a positive budget with two decimal places and a three-letter currency. Currency stays fixed on edits; one budget per currency can be archived/restored without deleting history. **Link recorded expense** associates an existing owned Finance expense; **Unlink** removes attribution. These actions never change the amount, account or account balance. To move an already-linked expense, unlink it first or use its existing project. Plans compare lifetime linked expenses across all booking dates by account currency, excluding income and principal transfers. Archived budgets are excluded from planned totals while their linked expenses remain visible. Currencies are never converted or combined. Another workspace member, including the workspace owner, cannot read your budgets or expenses.

The project view combines visible task progress, unarchived milestones and **your recorded time**, excluding running/discarded sessions. Recorded time retains the project attribution captured when that work was logged; later task moves do not rewrite history. CSV exports contain the selected project or current filtered project list, separate currency rows and formula-safe labels. Milestone CSV respects the archived toggle. All projects, milestones and budgets are paginated; loading errors disable exports. Workspace JSON includes the loaded planning records. No milestone reminders, payments or external messages are created.

## Export, backup and restore

The UI exports the complete visible ledger to CSV and loaded workspace records to JSON. CSV cells are escaped and formula prefixes are neutralized. Calendar and notes load at most 500 records each; projects, tasks and their organization/checklists use full pagination; activity and notifications have smaller limits. Goals, milestones, habits and their histories use full pagination, as do the newer record modules described above. These user exports are convenient snapshots, not full infrastructure backups. Financial ledger pagination fetches all visible entries for accurate balances; large-ledger server aggregation is a future performance milestone. Monetary writes validate two decimal places and PostgreSQL uses NUMERIC(14,2). UI calculations use integer cents; displayed summary cards round to whole currency units while transaction tables preserve cents.

1. **Database:** periodically use `supabase db dump --linked` for schema and data according to the official CLI backup procedure. Store encrypted snapshots outside Supabase and GitHub. Include roles, migrations, auth identities and workspace memberships in the recovery plan; Supabase-managed Auth objects require the provider's documented migration procedure rather than a blind application-only dump.
2. **Storage separately:** enumerate every private bucket, download all objects with privileged tooling, and save a manifest of bucket/path, content type, size and checksum. Back up bucket settings/policies as well. Database backups do **not** include object contents. Keep service credentials out of logs and source control.
3. **Restore database:** create a clean staging project, restore the schema/migrations and Auth identities with the provider-supported procedure, restore application rows preserving original UUIDs and foreign keys. Review changed project URLs and key rotation. Validate row counts, ownership and RLS tests before switching the frontend.
4. **Restore files:** recreate private buckets, upload each manifest entry under its original path, verify checksums, then reconcile attachment metadata. Test an authorized signed download and rejection from another account.
5. Run a periodic restore drill using a separate project. Never test a restore by overwriting production. Record backup time and checksums; keep multiple generations and monitor failed jobs.

Check current Supabase plan limits in the project dashboard. A free project can pause after inactivity; handle paused-project errors by restoring service in the Supabase dashboard. Monitor database/Storage sizes, egress and usage. Avoid unnecessary Realtime subscriptions and scheduled calls. PWA caching includes static build assets only, never API responses, exports or private uploads.
